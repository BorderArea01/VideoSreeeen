# 正式视频转发与画质、连续性

2026-10-19。用户确认先前备用通道能播放，要求改为正式通道，并反馈不清晰和卡顿。

## 修改

- 房间确认共享后立即连接独立视频 WebSocket，取消约 15 秒的 ICE 等待及并行 WebRTC 视频编码。房间与聊天通道、完整共同缓存仍独立。
- 默认高清目标从 1.2 提至 4.5 Mbit/s，音频从 96 提至 128 kbit/s；提供方可选流畅 1.8、高清 4.5、高画质 6 Mbit/s。源画面的真实质量仍由提供端决定，没有把重编码称为无损原画。
- 输出块从 500 缩至约 200 ms，请求约 1 秒关键帧。服务端输入桶同步调整到约 8 Mbit/s，保持 64 KiB 包和 2 MiB 积压限制；按累计序号批量确认减少往返消息。
- 约 2.5 秒起步缓冲后播放；缓冲耗尽时先补足缓冲，可增加到 5 秒。使用小幅调速维持缓冲，将频繁的硬跳转改为仅在延迟超过 12 秒时追赶。付出的代价是短暂观看延迟。
- WebM 缓存初始化和近期关键帧，按 EBML 边界解析 SimpleBlock / BlockGroup；最多 8 MiB，视频不落入持久化存储。新观众以独立发送/确认序号接入，兼容时无需重启现有流；离开也不重启其他观众的编码。最后一人离开清理历史并停编码，下次新建流。其他容器格式仍可能需要重启。
- 早期真实多观众测试发现 Chrome 使用 BlockGroup，首版仅处理 SimpleBlock，后来加入者未收到可用关键帧。已依据实际测试数据及 WebM 规范补齐，并重新完成验收；未将失败版本部署。

## 验证

- 最终 `npm run verify` 通过，39 项测试、类型、构建与 Worker dry-run。测试包括 EBML 碎片边界、编码数据中的伪 Cluster 字节、BlockGroup 引用、历史上限、加入离开不重启与最后一人离开后的重新开始。
- 修正后的本地 720p 动态画面与音轨通过：首屏约 5.6 秒，未创建视频 WebRTC 连接；初次检查视频解码 13 帧，音频解码 16303 字节，起步缓冲约 2.45 秒，卡顿计数 0。
- 新观众实际加入、解码并离开后，原观众的 MSE URL 与提供端编码器数量不变。连续六秒分别解码 14、10、13、11、13、11 帧，均未暂停。该数据来自隔离的生成样片，不冒充用户远程网络已通过。
- 本地文件经正式 WebSocket 通道播放 960×540 视频，暂停、拖动、重新加入和停止清理通过；音频实际解码字节大于零。
- 本地 workerd 的真实二进制传输、休眠恢复、成员身份隔离、停止清理、图片及聊天回归通过。保留的 WebRTC 标签页采集、预览、音轨、取消重试、移动布局和停止回归通过。

最终画质下拉项验收通过：默认编码器目标 4.5 Mbit/s，切换流畅后实际新编码器目标为 1.8 Mbit/s，观众重新播放。最终本地首屏 5544 ms，六秒分别解码 12、12、12、12、13、11 帧，无页面错误，重新加入和停止清理通过。证据保存在 `.local/primary-video-local-evidence.json`。

线上部署元数据在完成后补充。不会把源码完成或本地样片通过当作用户主观清晰度、所有网络和苹果真机均已验收。
