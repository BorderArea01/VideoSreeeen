# 播放方式与共同播放验证

2026-10-19。用户反馈模式入口混乱，只有标签页共享直观可用，要求核实原有共同播放并整理 UI。

## 链路与使用条件

- Bili-SyncPlay 的扩展运行在每位成员的 B 站页面上，控制原播放器并通过 WebSocket 同步状态；没有把提供端画面重编码后发送给所有人。依据：[项目架构](https://github.com/sky1wu/Bili-SyncPlay/blob/main/docs/architecture.md)。本项目的采集、编码、转发和短缓冲是另一条链路，会带来额外画质损失与延迟。
- 本项目原有共同播放仍保留：可播放视频源各自加载；Windows / Android 原站视图通过页面桥接采样并控制播放器。浏览器页面没有扩展权限，不能自动控制其他网站的播放器；依据：[同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)。
- 视频直链仍受源站临时地址、防盗链、跨域访问与设备解码支持影响。此轮实际视频验证使用 CC0 MP4，不把它冒充所有 HLS、B 站、喜番或蜜柑页面兼容性通过。原站登录和权限不绕过。

## 修改

- 独立的播放方式选择器：共享画面、共同播放、本地视频。只展开相应操作；键盘方向键、Home / End 可选择。房间当前方式单独显示，切换输入面板不会修改播放状态或换片。
- 默认提供共享画面；未打开原站的操作折叠，Windows 显示应用内原站打开与共享路径，不能采集的设备明确显示接收或本地文件选项。
- 共同播放输入原站页面时，网页版直接说明无法控制跨站播放器。只有明确选择“改用共享画面”才进入提供流程；不会用尚不能播放的页面替换正在工作的直链。原生原站控制、自动源识别、手动提取及缓存路径保留。
- 本地视频独立显示文件按钮及格式说明；实时画质、停止共享和状态集中在当前视频区域。共同缓存默认关闭，仅在当前源可用时显示；不与实时共享并列冒充通用入口。
- 无媒体、无法播放和实时屏幕共享隐藏无效控制；实时共享页脚说明进度在原站操作。播放失败提示区分源地址问题，不再将播放失败一律解释成 HLS 完整缓存限制。

## 自动与浏览器证据

- `npm run verify`：40 项测试、格式、类型、构建、Worker 类型与 dry-run 通过。
- `scripts/playback-modes-check.ts`：两个真实浏览器独立解码 960×540 MP4；观众开始播放、提供方暂停、观众拖动到 1 秒、提供方设置 1.25 倍速均作用于两个实际视频元素。切换面板和输入不支持的 B 站页面未发送换片或时间线操作，原视频保留。键盘选择和 390 像素布局通过，页面错误为零。
- `scripts/native-sync-check.ts`：实际 Windows Electron 原站视图打开受控页面，网页成员接收已识别的公开视频源。共同播放没有设置 broadcast，也未采集或重编码。播放、暂停、拖动和倍速控制到原站实际视频；连续四次原站采样保持暂停、1 秒与 1.5 倍速。此项是 Windows 原站桥接与浏览器联动，不代表两台 Windows、Android 真机或特定第三方网站已验收。
- `scripts/broadcast-check.ts`：本地文件经正式视频 WebSocket 解码；真实提供端暂停、拖动、倍速，重新加入和停止清理通过。
- 已目视桌面三种方式与手机控件截图，证据位于 `.local/screenshots/modes-*.png`。结构化记录位于 `.local/playback-modes-local-evidence.json`、`.local/native-sync-evidence.json`、`.local/broadcast-evidence.json`。
- 原生 WebContentsView 独立于页面截图，另捕获本测试拥有的原站视图 `.local/screenshots/native-common-source.png`，已目视实际样片画面；没有截取用户桌面或其他应用。
- 新版入口的 onboarding 回归通过，包括原站链接明确切换、邀请、重连、聊天、无效视频源和手机布局。正式视频转发回归通过，实际解码、声音授权、画质切换、新观众、提供者重连、停止清理均通过，页面错误为零。
