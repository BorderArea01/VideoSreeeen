# 共同播放反复短暂停顿与校时跳变

2026-10-20 用户反馈视频可以播放，但频繁停顿约 2 秒，并明确“所有人差不多同时停顿”。这不能继续只按单台手机 HEVC 解码失败处理。

## 真实片源观察

在正式入口建立独立测试房间，Windows 浏览器与 Pixel 7 浏览器资料共同播放同一 AL 视频，另开一个不参与同步的普通 video 元素作参考，连续观察 60 秒。没有加入用户原房间、读取其凭据或操作 Android 设备。

- 原实现其中一端主动修改进度 5 次，另一端 3 次，包含向前和向后约 1～2 秒的跳转。
- 部分自动跳转发生在已有 10～25 秒缓冲、readyState 为 4 时，并引发 seeking / waiting。这些停顿不能解释成单纯没有下载到视频。
- 也观察到实际缓冲不足：一端在约 6.16 秒只剩约 0.009 秒缓冲，产生真实等待。因此同步缺陷与源站加载波动可以同时存在，不能把所有停顿归为其中一个原因。
- 普通 video 元素初始加载较慢，开始后未记录到相同的前后跳转；参考播放和双端测试仍共享维护机器网络，不代表异地网络已验收。

## 识别出的机制与改动

旧实现每次 pong 都令播放基准为 `收到时刻 - 服务端 age - RTT/2`，每个状态快照也会用最近一次 RTT 重设基准。非对称网络延迟或排队会让这个中点估计误差达到数秒；后续正常心跳又反向修正。播放器每 300ms 检查进度，漂移超过约 1.2 秒便硬跳转，因此即使视频有足够缓冲，校时波动也会触发解码重定位。

新 `PlaybackClock` 用请求发出与响应到达之间的时间范围约束服务端播放基准，而非将每个 RTT 中点直接当成真值。保留最近一分钟、最多 12 个相容样本区间，只有新证据表明当前基准超出相容范围时才收紧；不相容样本不污染基准。同一媒体、缓存代次与播放版本的聊天／成员快照不再重置时钟。

新播放版本、手动拖动、换片和重连仍重新采用权威时间线，不延迟显式操作。房间权威状态、去重和冲突协议不变；成员列表和底部 RTT 继续使用服务端挑战样本，不平滑或伪造展示值。

诊断补充实际缓冲余量、播放位置、当前速度、掉帧数、自动／手动跳转次数，以及校时样本数和不确定范围；不支持的掉帧统计显示未知，不上传服务器。

## 自动验证

`npm run verify` 通过 68 项测试、格式、构建、Worker 类型与 dry-run。新增用例覆盖往返 4 秒的单向排队、相反方向的排队、同版本快照、显式新版本、矛盾／旧代次样本及重连显示连续性。

`npm run test:playback-clock` 使用真实长视频、独立浏览器资料和真实房间 WebSocket，仅在测试观众端将部分 pong 响应延后 4 秒，并持续发聊天触发同版本快照；不篡改服务端 RTT 挑战或用户可见数值。通过 `VS_EXPECT_CLOCK_JUMPS=1` 可对旧前端检验复现，新前端要求投影时间线不跳变、不向后跳或在充足缓冲时硬跳，手动拖到 45 秒仍立即生效并继续出帧。这个测试采用 W3C 托管的公开 Sintel MP4 示例，避免把稀饭源站下载波动混入纯校时对照；真实 AL 片源观察另行保留。

参考成熟播放器将缓冲状态与调速分开处理的设计：[Shaka PlayRateController](https://shaka-project.github.io/shaka-player/docs/api/lib_media_play_rate_controller.js.html)。本轮没有引入 Shaka 或复制其代码。

受控旧版对照已通过：正式入口旧前端 `9d73c3f`、Sintel 真实视频、观众端 4 秒延迟 pong 与聊天快照，25 秒观察中自动跳转 4 次，前后约 1.86～2.11 秒。底层视频 readyState 为 4，表明不是缺少可播放数据造成的这些重定位。脱敏摘要为忽略目录 `.local/playback-clock-before.json`。

新版本地同条件对照通过：自动跳转 0 次、投影时间跳变 0 次；两端均 854 像素、728 帧，播放位置为 30.136896 / 30.135608 秒，相差约 0.0013 秒；手动跳到 45 秒后两端均继续解码，无页面错误。摘要为 `.local/playback-clock-after.json`。测试准备期间也遇到真实下载／解码停顿，故验收同时记录缓冲余量，区分数据不足后的向前追赶和遥测造成的前后跳变，未通过放宽同步时间差掩盖问题。
